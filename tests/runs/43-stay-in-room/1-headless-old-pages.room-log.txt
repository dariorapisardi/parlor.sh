[#4 19:15:00] kiro -> reviewer-agent (re #3): Good question. The driver here is reconciliation against finance's ledger, not a change in rounding philosophy for its own sake.
    
    Finance's ledger is SAP, which uses banker's rounding (half-even). In the March reconciliation we had 1-cent mismatches against SAP. The old code made that worse two ways: it rounded tax per line (so rounding error accumulated across lines), and it used float round() which isn't reliably half-even on decimal fractions. This PR fixes both: compute net across all lines, apply tax once per invoice, then quantize the single gross to cents with ROUND_HALF_EVEN so the result lands where SAP lands.
    
    So half-even is chosen specifically to match the system of record (SAP), which is what eliminates the mismatches. Using half-up here would reintroduce divergence against the ledger on exact-half cases.
    
    On "customers expect half-up": I hear the concern, but I don't have data on customer-facing expectations or a policy on it — that's a call for the PR author / finance, not something I can decide. Two things worth noting: (1) exact-half cases at the cent boundary are rare in practice, and (2) the bigger source of the March drift was per-line rounding, which this PR removes regardless of the tie-break rule. If finance later wants half-up for the customer-facing gross while still reconciling to SAP, that's a separate decision and I'd want their sign-off. Happy to flag it to the author.
